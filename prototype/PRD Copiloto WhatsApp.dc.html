01 — Contexto

Problema e oportunidade

Os vendedores da MR Digital conduzem negociações de cursos de implantodontia digital majoritariamente por WhatsApp. Cada lead tem uma persona, um estágio no funil e um histórico de conversa distintos — e a qualidade da próxima mensagem determina a conversão. Hoje essa decisão é manual, depende da memória do vendedor e não é consistente entre a equipe.

O Copiloto de Vendas centraliza, em uma única superfície conversacional, três capacidades: (1) responder dúvidas sobre o portfólio e a metodologia comercial, (2) carregar o perfil e o histórico completo de um lead no contexto e (3) sugerir mensagens prontas para enviar, com a estratégia por trás de cada uma.

Em uma frase

"Como vendedor, quero perguntar ao copiloto qual é a melhor mensagem para um lead específico e receber opções prontas para copiar — fundamentadas no perfil e no histórico dele."

02 — Objetivos

Metas e não-metas

✓ Metas
  • Reduzir o tempo para redigir a próxima mensagem de um lead.
  • Padronizar a qualidade da abordagem entre toda a equipe comercial.
  • Tornar a metodologia SPIN e os gatilhos por persona acionáveis no fluxo de trabalho.
  • Servir como base de conhecimento viva sobre cursos e funil.
✕ Não-metas (v1)
  • Enviar mensagens automaticamente pelo WhatsApp (v1 é copiar e colar).
  • Integração bidirecional com a API oficial do WhatsApp.
  • Edição do CRM / movimentação de leads no funil a partir do copiloto.
  • Automação de cadências ou disparos em massa.

04 — Usuários

Quem usa

V
Vendedor / Consultor comercial
Usuário primário. Conduz negociações no WhatsApp e precisa decidir rápido a próxima mensagem. Quer respostas com a estratégia explícita, não só o texto pronto.
C
Coordenador comercial
Usuário secundário. Usa os comandos de visão geral (/weekly-review, /at-risk) para acompanhar o pipeline e padronizar a equipe.
05 — Escopo funcional

As quatro capacidades

A. Chat com base de conhecimento
Sem nenhum lead anexado, o copiloto responde sobre cursos (Imersão, Master 3.0, Especialização), as 4 personas e suas taxas de conversão, a metodologia SPIN, leads em risco e o resumo da semana.
B. Anexar lead com @
Digitar @nome abre um seletor de leads. Ao escolher, o perfil (persona, estágio, ticket, origem, telefone) e o histórico completo de mensagens são carregados no contexto, exibidos em um chip recolhível acima do campo de entrada.
C. Comandos com /
Digitar / abre um menu de comandos: /weekly-review, /today-tasks, /at-risk, /personas, /courses, /spin. Filtra conforme digita; Enter executa o primeiro resultado.
D. Sugestão de mensagens
Com um lead anexado, a resposta traz uma Análise (a estratégia) seguida de 3 variantes de mensagem com tons distintos (Consultivo, Objetivo, Caloroso), cada uma com botão Copiar.

07 — Arquitetura no stack atual

Componentes & estado

A página vive na rota /copiloto dentro do <Layout/> existente (sidebar + topbar), seguindo o padrão das demais páginas em src/pages. Stack: React + Vite + Tailwind v4, ícones lucide-react, fontes Manrope/Inter.

src/ ├─ pages/ │ └─ Copiloto.jsx // container: estado + orquestração ├─ components/copiloto/ │ ├─ EmptyState.jsx // saudação + composer central │ ├─ Composer.jsx // textarea + @ e / detection │ ├─ MentionMenu.jsx // seletor de leads │ ├─ CommandMenu.jsx // menu de slash-commands │ ├─ LeadContextChip.jsx // chip recolhível │ ├─ MessageList.jsx // thread + auto-scroll │ └─ DraftCard.jsx // variante + copiar ├─ hooks/ │ └─ useCopilot.js // reducer da conversa └─ lib/ └─ copilotApi.js // chamadas ao backend

Gestão de estado

Um useReducer em useCopilot.js mantém: messages[], attachedLead, input, isTyping e o estado dos menus (mention / slash). A detecção de @ e / usa regex sobre o final do input — exatamente como no protótipo. Sem necessidade de store global; o estado é local à página.

Fonte de dados

No protótipo, leads, personas e histórico vêm de src/data/mock.js. Na implementação, copilotApi.js substitui o mock por chamadas reais, mantendo o mesmo formato de dados para troca transparente.

08 — Modelo de dados

Contratos

Lead { id, name, initials, persona, stage, course, value, source, phone, lastContact, angle, // ângulo recomendado (string) history: [{ fromLead: bool, text, at }] } Message { id, role: "user" | "assistant", kind: "text" | "drafts", text?, reasoning?, variants?: Draft[] } Draft { tone: "Consultivo" | "Objetivo" | "Caloroso", text }
09 — Endpoints da API
GET/api/leads?q={query}
Autocomplete do seletor @. Retorna leads resumidos (id, nome, persona, estágio).
GET/api/leads/{id}/context
Perfil completo + histórico de mensagens para carregar no contexto ao anexar.
POST/api/copilot/chat
Corpo: { messages[], leadId?, command? }. Retorna uma Message (texto KB ou drafts com Análise + variantes). Suporta streaming (SSE) para o indicador de digitando.
Camada de IA
O backend monta o prompt com o perfil + histórico do lead e injeta a base de conhecimento (cursos, personas, SPIN) como sistema. As respostas drafts devem retornar JSON estruturado para renderização determinística dos cards.
10 — Faseamento

Roadmap de entrega

Fase 1 — UI shell + drafts mockados (~1 sem)
Portar o protótipo para componentes React no stack. Mention, chip de contexto e cards de variante rodando sobre mock.js. F-01 a F-05.
Fase 2 — KB + slash commands (~1 sem)
Modo base de conhecimento e menu de comandos. F-06 a F-09.
Fase 3 — Backend + IA real (~2 sem)
Endpoints reais, geração via LLM com prompt estruturado, streaming. Substitui o mock.
Fase 4 — Persistência + refinamentos (~1 sem)
Histórico por sessão, regenerar variantes, telemetria de aceite. F-10, F-11.
11 — Requisitos não-funcionais
·Primeira resposta visível em <1,5s (com streaming).
·Acessível por teclado: Enter envia, Shift+Enter quebra linha.
·Responsivo dentro do shell existente (desktop-first).
·Dados de lead nunca persistidos no cliente além da sessão.
12 — Riscos & questões em aberto
